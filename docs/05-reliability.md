# 05 · 可靠性：讓失敗大聲

九個專案下來，最貴的 bug 幾乎都有兩個共同特徵之一：

1. **靜默失敗**——功能沒有啟用，但輸出看起來一切正常
2. **小規模能過的假設**——在 5 分鐘的片、9 支素材上從沒出事，規模一放大就同時現形

以下每一則都是真實發生過的，附上症狀、根因、怎麼找到的、怎麼修。

---

## 一、靜默降級

### 切點精修默默跳過
**症狀**：成片的字尾偶爾被切掉，但渲染全程沒有任何錯誤。
**根因**：用系統 Python 執行渲染器，缺少數值運算套件；精修函式捕捉到 import 失敗後退回
「不精修」——全部 14 段都跳過了，沒人知道。
**修法**：啟動時檢查依賴並大聲警告；渲染結束時印出降級摘要（「N 段精修被跳過」）。

### 檢索融合默默關閉
**症狀**：B-roll 引擎輸出「融合=關閉」，看起來像正常的策略判斷。
**根因**：以模組方式（`python -m`）呼叫時，搜尋路徑不同，視覺索引模組 import 失敗，
程式退回純關鍵詞模式。設定檔裡融合明明是開的。
**修法**：兩種模組路徑都試；都找不到時明講「設定為開啟卻走到這裡，代表環境有問題，
不是策略決定」。

### 依賴清單不完整
**症狀**：專案搬到新位置重建虛擬環境後，整條流程跑不動。
**根因**：依賴清單只列了 Web 服務的三個套件，數值運算、深度學習框架都是手動裝的。
缺數值套件**不會報錯**——它會觸發上面第一則的靜默降級。
**修法**：補齊並鎖定版本；註明 Python 版本限制（框架當時沒有最新版 Python 的 wheel）。

## 二、「看起來存在」的檔案

macOS 的雲端同步在磁碟空間吃緊時，會把本機檔案清成**佔位檔**：檔案大小欄位仍是原值，
實際佔用的區塊數為 0，讀取時回傳 0 bytes **且不報錯**。專案目錄剛好在同步範圍內。

### 轉錄全滅，但退回機制從未觸發
**症狀**：43 支素材的轉錄全部失敗，錯誤訊息是「模型資料無效」。
**根因**：主要 ASR 模型被清成佔位檔。腳本用「檔案大小 > 0」判斷模型是否存在——佔位檔的
大小欄位仍是 874 MB，判定通過，於是「找不到大模型就退回中模型」的機制從未觸發。
**修法**：改成實際讀取一段內容來判定可用性。

### 單一壞檔讓整批中止
**症狀**：音訊抽取做到 19/46 就停了，結尾統計只顯示「數量不足」。
**根因**：腳本開了「任一指令失敗即中止」；一支讀不到的素材讓後面 27 支全部沒跑，而且看
不出是哪一支壞了。
**修法**：讀不到的素材跳過，結尾**指名列出**跳過了哪些、可能原因與補救方式。

### 版本控制卡住 50 分鐘
**症狀**：一次提交跑了 50 分鐘沒結束。
**根因**：被追蹤的分析檔案裡有數百個佔位檔，提交時重整索引要讀它們，其中某個的回補卡住。
**怎麼找到的**：看 CPU 時間——50 分鐘牆鐘只用了 0.17 秒 CPU，它不是在算，是在等。
**修法**：把整個專案搬出同步範圍。搬完後同一次提交幾秒完成。

### 證據標準
這件事我判斷錯過一次。更早之前有一支成片讀取極慢，我宣稱「決定性證據顯示是雲端清除」——
但檔案的實體大小欄位與成功的讀取都推翻了這個說法，真正原因是磁碟 97% 滿造成的碎片化。

第二次真的遇到時，證據是：**區塊數為 0、帶有佔位旗標、同目錄的對照檔正常**；而決定性的
一條是——連一個從網路下載、跟相簿毫無關係的模型檔也被清掉，所以不是相簿的機制，是整個
文件夾的同步。

### 搬家本身也有坑
- **整棵樹一次搬會逾時**：搬出同步範圍時，系統必須逐檔解除託管（遇到佔位檔還要先下載），
  超過時限就整個失敗。所幸改名是原子操作，沒有資料損失。拆成逐項搬就能通過，而且過程中
  順便把所有佔位檔都下載回來了
- **絕對路徑的符號連結**：模型目錄是用絕對路徑連過去的，專案搬走了，模型實體還留在同步
  範圍裡。更糟的是我第一次驗證「零佔位檔」時，目錄走訪預設不跟隨符號連結，模型根本沒被
  掃到——**驗證本身不完整**。改成實體目錄後才真正解決

## 三、小規模能過的假設

### 固定逾時值
**症狀**：20 分鐘的片在燒字幕那一步逾時失敗。
**根因**：逾時寫死 900 秒。燒字幕要把整支片重編一次，對 5 分鐘的片綽綽有餘。
**修法**：「基礎值 + 6 × 片長」。逾時的用途是抓卡死，不是當編碼時間預算，倍率留足餘裕。

### 選到素材最後半秒就失敗，錯誤訊息還指錯方向
**症狀**：渲染失敗，訊息說「系統高負載導致 ffmpeg 靜默截斷，請等負載降下來再重跑」。
**根因**：選段的結束點正好在素材檔尾，加上尾端 padding 後要求切到檔尾之後——ffmpeg 只能
切到檔尾，片段變短，時長檢查攔下。**跟負載毫無關係。**前幾個專案都剛好沒選到素材末端。
**修法**：padding 加上素材長度天花板，並在能量精修之後再鉗一次（精修也可能把切點推過檔尾）；
鉗制時印出「素材僅 N 秒」，不再偽裝成負載問題。

### 字幕在畫面上停留 17 秒
**症狀**：一句十個字的話，字幕掛了 17.4 秒。
**根因**：ASR 把講者說完之後的長靜默併進了同一段。字幕沿用段落的時間範圍。
**修法**：依字數設顯示上限。畫面的留白保留（那段靜默本身有意義），只是字幕不再賴著。

## 四、先量再猜

### 「索引程式有問題」其實是磁碟
**症狀**：視覺索引在三個專案上反覆「失敗」，每次都卡在編碼階段，一度被懷疑是程式問題。
**怎麼找到的**：比較 CPU 時間與牆鐘時間。限縮到 3 支素材測試：CPU 17 秒、牆鐘 18 分 16 秒，
使用率 1%。最嚴重的一次：**79 分鐘牆鐘，1.27 秒 CPU**。
**根因**：磁碟 97% 滿，page cache 容不下深度學習框架的數千個檔案，每次 import 都重讀磁碟。
同時渲染器連自己剛寫好的片段都打不開（`Operation timed out`）。
**結果**：清出空間後，同一份程式碼一次建成索引，模型載入 0.2 秒。程式從來沒有問題。

### 背景執行的提交永遠不會結束
**症狀**：版本控制提交在背景執行後一直沒結束，之後所有寫入都失敗。
**怎麼找到的**：2 分 52 秒只用了 0.07 秒 CPU，狀態是睡眠。
**根因**：提交訊息透過標準輸入傳入，背景執行時標準輸入是空的，程式永遠在等；留下的鎖檔
讓後續所有操作失敗。
**修法**：訊息改寫成檔案再傳。清鎖檔前先確認沒有活著的程序。

## 五、我自己造成的

### 修正方向時把影片轉成顛倒
處理側躺的素材時，用轉置濾鏡重新編碼——但原檔的旋轉 metadata 被複製到輸出，跟轉置
疊加，影片變成上下顛倒。抽幀比對才發現。現在的流程是：重新編碼後一定再查一次旋轉
metadata，並先用「不自動旋轉」模式看原始儲存方向再決定怎麼修。

### 違反自己定的順剪規則
見 [`02-editorial-method.md`](02-editorial-method.md#順剪鐵律)。守衛是對的，我是錯的。

## 共同的修法原則

- **檢查「可讀」而不是「存在」**：大小欄位、檔名、目錄項目都可能在說謊
- **降級時要說話**：退回備案可以，但要在輸出裡明講「退回了、為什麼、影響範圍」
- **錯誤訊息要指對方向**：一個歸咎於「系統負載」的錯誤訊息，會讓人去等一個永遠不會
  消失的問題
- **用 CPU 時間判斷是否還活著**：牆鐘時間只告訴你過了多久，不告訴你它在做什麼
- **逾時與門檻要隨規模縮放**，或至少寫清楚它假設的規模
- **驗證本身也要被驗證**：「掃描結果零問題」可能只是掃描沒掃到
